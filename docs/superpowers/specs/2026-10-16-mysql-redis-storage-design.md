# MySQL 与 Redis 通用存储规则及迁移设计

状态：待 Coco 审阅的设计草案。方向和大步骤已获认可，本文中的技术选型、默认配置和执行清单尚未获实施确认。

## 1. 目标与范围

按用户需求中的恢复、一致性、权威性、时效、隔离和并发要求选择存储。规则不依据页面、卡片或业务名称分配数据库；新增需求沿用同一决策方法，不增加业务到存储的映射分支。

首期部署目标已确定为单服务器。本文建议首期保留单 Web 进程及既有进程内任务执行方式，引入 MySQL 持久存储与 Redis 展示缓存；独立任务进程、多 Web 进程及任务队列不随存储迁移自动引入。该首期进程方案仍需 Coco 确认。

迁移范围建议为 SmartTest Web 自身的持久存储、缓存及直接调用链，包含会话与平台凭据适配。既有外部只读数据库独立保留，不与应用写库混用；其他模块独立使用的 SQLite 不因名称相同而删除。迁移不改变业务规则、权限、刷新授权、调度时间或结果有效性标准。

## 2. 需求必须先声明的属性

每个需要存储的需求必须说明以下属性，由业务 owner 在设计及验收中维护，不建立数据库自动猜测器。

| 属性 | 必须明确的问题 |
| --- | --- |
| 权威性 | 是否决定业务事实、授权、动作范围、执行结果或审计证据？ |
| 恢复要求 | 进程重启、数据库重启或服务器故障后必须保留什么？允许丢失多少？ |
| 可重建性 | 是否存在独立、可靠且可访问的重建来源？重建代价和耗时是多少？ |
| 一致性 | 哪些修改必须原子完成？能否接受旧值，最多多久？ |
| 隔离 | 数据属于账号、真实会话、共享授权范围还是执行实例？ |
| 生命周期 | 何时产生、替换、失效、清理？到期后的行为是什么？ |
| 依赖 | 结果依赖哪些数据版本、规则版本、权限边界和时间窗口？ |
| 负载 | 读取和写入频率、数据体量、并发峰值、延迟目标是什么？ |

缺少影响正确性的属性时先明确需求，不通过额外兜底或扩大数据范围掩盖。

## 3. 通用归属规则

### 3.1 MySQL：权威持久数据

满足下列任一条件的数据，由 MySQL 或项目已有专用安全持久 owner 保存：

1. 用户要求跨重启保留，且不能仅依赖其他可靠来源恢复。
2. 决定业务动作的精确范围、已提交意图、有效结果或审计证据。
3. 要求事务、唯一性、关联完整性、并发修改校验或可靠追溯。
4. 重建会访问远端、依赖可能变化的历史信息，或无法在允许时间内完成。

远端数据在本系统内承担权威查询依据时，仍属于需要持久保存的数据，不能因被称作“缓存”就放入可淘汰存储。

凭据继续经安全 owner 加密或使用系统安全存储；密钥不得与密文一起迁入普通业务表、配置样例或日志。

### 3.2 Redis：可重建缓存

同时满足以下条件，才适合进入可淘汰的 Redis 缓存：

1. 存在独立的权威来源，删除缓存不丢失用户已提交信息。
2. 能按明确规则重建；缓存命中与未命中不改变业务结果及授权。
3. 重复读取或计算具有实际成本，缓存收益能够测量。
4. 已定义缓存标识、有效性、TTL、容量和故障行为。

Redis 缓存不是第二个权威 owner。不得只把尚未落库的业务结果写入缓存，不得让业务动作从展示缓存获取权威资源集合。

### 3.3 Redis：短期协调及消息

需要跨进程传递信号、共享短期进度或协调执行时，可以使用独立的 Redis 运行期能力；这与缓存是不同契约。

- 运行状态必须包含执行归属、有效期限和中断识别；恢复出旧状态不证明原执行仍然活着。
- 需要可靠交付的消息必须定义持久接受点、确认、重试、去重和幂等；使用成熟队列，不自行实现简化队列。
- Redis 租约只减少重复工作，不能作为防止旧执行发布结果的唯一保证；有效结果发布仍由持久存储的版本校验保障。
- 不可重建且不允许丢失的数据，不能仅因 Redis 开启 AOF 就改判为普通运行期状态。

首期不启用跨进程协调或消息队列；后续需求满足这些条件时，先确认其丢失与执行语义。

### 3.4 前端与进程内存

前端保存未提交控件和可丢弃展示副本，不能决定权威数据范围。进程内存保存当前执行对象、连接和短期计算状态，不能承载跨重启必须恢复的业务数据。

## 4. Redis 持久化与资源隔离

| 存储契约 | 建议策略 | 恢复含义 |
| --- | --- | --- |
| 完全可重建的展示缓存 | 首期不启用 AOF/RDB；所有键有 TTL，配置 maxmemory 与 allkeys-lru | 重启后为空，按需从权威来源重建 |
| 允许重启失效的协调状态 | 不依赖磁盘恢复证明状态有效 | 由执行归属及期限识别中断 |
| 要求重启后继续交付的消息 | 单独评审持久队列方案；Redis 方案评估 AOF everysec、备份及成熟队列契约 | 仍需接受丢失窗口与重复交付，不承诺恰好一次 |

缓存与不可淘汰的队列若同时使用，采用独立实例和内存预算，不能只用 Redis 逻辑 DB 编号隔离淘汰策略。AOF everysec 通常仍有约一秒的数据丢失窗口；不满足用户恢复要求时必须调整方案。

TTL 的意义是缓存回收及限定时效，不是远端刷新计时器，也不能取代版本更新。具体值必须根据允许旧值时间、重建成本及数据体量确定，不统一硬编码到所有需求。

## 5. 应用分层与透明边界

建议沿用以下职责，不创建包办所有业务的统一巨型类：

```text
前端 → 稳定 API → 既有业务 Service → 既有 Repository → MySQL
                              └→ 统一缓存基础能力 → Redis
```

- 前端接口表达用户意图、展示周期、结果状态等业务契约，不暴露数据库类型、SQL、Redis key 或内部连接信息。
- Service 负责权限、动作范围、刷新授权、结果有效性和发布时机；存储层不得自行改变这些规则。
- Repository 保持唯一数据读写 owner，使用统一连接及事务入口；不在路由、前端或缓存工具中复制查询逻辑。
- 缓存基础能力只复用 key 编码、序列化、TTL、超时、容量配置和命中统计；业务依赖版本由原业务 owner 提供。
- SQL 连接和事务建议复用 SQLAlchemy Core；schema migration 建议使用 Alembic；Redis 使用 redis-py。均为拟议依赖，实施前核对维护状态、驱动兼容及依赖链并锁定版本。
- 首期不强制引入 ORM、不做自动业务路由、不做 SQL 方言字符串替换层，不按资源名称写 if/else 选择数据库。
- MySQL 事务不能与 Redis 写入视为一个原子事务；数据库提交成功不因缓存写失败而撤销业务成功。

缓存故障行为必须属于显式契约：本方案建议展示缓存超时或不可用时，从 MySQL 完成同一授权范围的读取并记录状态；MySQL 不可用则明确失败，不把旧缓存冒充当前有效结果。运行期协调和消息失败不能套用展示缓存的处理方式。

## 6. 通用读取、更新与发布流程

### 6.1 读取

1. 认证、授权并从 MySQL 取得当前有效结果及必要依赖版本。
2. 使用版本、隔离范围、查询维度和聚合时间边界定位 Redis 展示缓存。
3. 命中返回统计正文；未命中从同一权威数据版本计算，写缓存后返回。
4. 权限相关字段、执行状态、进度和取消能力由当前请求单独组合，不随账号共享展示正文一起缓存。
5. 纯读取及缓存未命中不得启动远端更新。

首期仍进行轻量数据库版本读取，以避免建立第二份当前有效指针。大规模冷缓存重建应限制并发；具体预算在实现前按测量确定，不引入业务专属锁机制。

### 6.2 更新

1. 持久保存用户提交意图及版本，再按原有授权规则启动执行。
2. 外部 I/O 在数据库事务外进行，分批写入尚未发布的数据版本。
3. 在 MySQL 事务中校验执行仍有发布资格，再原子更新有效指针。
4. 新依赖版本生成新的缓存标识；旧键由 TTL 回收，旧请求只能写旧键。
5. 取消、失败或过期执行不能发布有效结果。已有有效数据依既有业务规则保留，不扩大范围。

结果依赖多份独立数据时，缓存版本必须覆盖完整依赖集合。读取计算应获得一致的依赖视图；不能用新版本标识存放旧依赖计算结果。时间窗口变化也属于依赖变化。

首期只缓存完整有效结果。执行中的部分结果继续遵循现有读取和可用性规则，避免为每次进度更新复制缓存生命周期。

## 7. 单服务器部署与关键控制项

只读盘点发现 Windows `MYSQL80` 服务已运行，WSL 已有 Ubuntu，尚未验证 MySQL 实例访问权限及 Redis 是否安装。先评估复用，禁止为迁移重置已有实例或复用不相关业务库。建议应用使用独立 schema 和最小权限账号。

拟议控制项统一放在后端配置 owner 中，下列名称尚未落地：

| 拟议名称 | 作用 | 本设计取值 |
| --- | --- | --- |
| `SMARTTEST_APP_DATABASE_URL` | 应用权威存储连接 | 指向独立 MySQL schema；凭据由安全配置注入 |
| `SMARTTEST_REDIS_CACHE_URL` | 展示缓存连接 | 独立 Redis 缓存实例 |
| `SMARTTEST_DB_POOL_SIZE` | 每进程数据库连接预算 | 待负载与服务器资源测量后确定，不沿用外部只读池预算 |
| `SMARTTEST_REDIS_TIMEOUT_SECONDS` | 限制缓存等待 | 实施前根据接口延迟预算确定 |
| 缓存策略中的 `ttl_seconds` | 每类需求的回收时间 | 按需求时效声明，不使用全局业务映射表 |
| Redis `maxmemory` / `maxmemory-policy` | 缓存容量及淘汰 | 容量根据机器资源确定，首期策略建议 `allkeys-lru` |

未确定的资源数值是环境测量项，不允许实施时静默猜测。安装与切换阶段须给出具体值供验收。服务不暴露公网数据库端口，连接信息不得进入日志。

多 Web 进程会复制连接池和进程内执行预算；若后续启用，必须先完成跨进程执行归属及全服务并发预算设计，不仅修改启动进程数。

## 8. 迁移与移除边界

1. 枚举本次应用调用链、schema、索引、迁移历史、平台凭据与测试依赖。该盘点只服务迁移验收，不成为存储规则。
2. 建立 MySQL schema、迁移及应用读写入口。替换 SQLite 方言及隐式 rowid 排序，显式维护唯一性、外键、大小写语义、JSON、时间与事务边界。
3. 用一致性 SQLite 备份演练导入，保留原 ID、关联和有效版本。对行数、唯一约束、关系、规范化内容摘要及用户可观察结果核对；不回填新业务数据。
4. 本设计建议单机短暂停写切换，不引入双写。停写必须同时覆盖请求写入、后台任务及调度；完成最终备份、导入和校验后才切换连接。
5. Redis 初始为空，从 MySQL 按需生成；迁移不触发远端查询、邮件发送或重跑历史任务。
6. 切换接受新写入前，失败可以退出切换并恢复原系统；接受新写入后不能直接回到旧 SQLite 文件，必须按明确的新数据恢复方案处理。
7. 验收通过后移除范围内 SQLite 运行路径、配置、依赖、测试替身及活动数据文件；历史设计记录保留，不为清除关键词篡改历史。
8. 迁移工具需要读取源格式时，与正常运行依赖分离。旧库备份按确认的保留期单独归档；活动数据删除前必须验证恢复。

停机窗口、备份保留期及切换后恢复目标需要 Coco 在正式切换前确认；本文不授权删除唯一数据副本。

## 9. 验收标准

- 新需求仅依赖第 2、3 节规则即可确定归属，无业务名称映射分支。
- 前后端 API 业务语义不变；权限隔离、共享边界和真实会话任务操作权限不变。
- MySQL 空库初始化、升级、并发写入、版本竞争和备份恢复通过真实实例验证。
- Redis 命中/未命中结果相同；过期、清空、重启和不可用时符合明确契约。
- 所有依赖版本及时间边界更新后，不能继续命中旧结果；迟到请求不能污染新版本。
- 权威业务动作只使用 MySQL 已确认范围，不从展示缓存或前端资源 ID 推断范围。
- 迁移校验通过；运行路径不再访问 SQLite；无自动回退到 SQLite。
- 记录接口延迟、数据库读取量、缓存命中率、重建耗时和远端请求量，对照迁移前同等负载；性能目标在压测前确认，不凭测试数量承诺吞吐。
- 完成受影响测试、真实服务启停、产品边界检查及完整 diff 清理。
